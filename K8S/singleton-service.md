# Singleton Service
A singleton service pattern ensures that only one instance of an application is active at a time and yet is is still high available. Applications can scale easily in k8s using things such as controller or using the `kubectl scale` command on single pods or through deployments. In some cases we want to allow only one instance of a service to run at a time, for example when we want to consume messages of a message broker in an order perserving manner.

Running multiple replicas of the same Pod creates an active-active topology where all instances of a service are active. What we need is an active-passive toplogy, where only one instance is active and all other instances are passive. This can be handled in our application or by kuberntes itself. The patterns are called and explained below:
1. Out-of-Application locking: This is done by Kubernetes and the application implementation itself is not aware of this constraint. The way to achieve this in K8s is to start a single Pod and back it up with a controller such as `ReplicaSet` in which the `replica: 1` is set. While the topology is not active-passive since there is no passive instance. But thanks to the controller the Pod is highly available if it is paired with health checks.

The main thing is the replica count shouldn't change under any curcumstance and we can achieve that with a `PodDistributionBudget`. This method is not completely without its flawse since the ReplicaSet under special conditions may bring up more than one instance for example when the node that is running the Pod is disconneted and the controller brings up another instance on a healthy node without making sure the unhealthy node is shut down. This can be done temporarily as well when we are moving the object to another node the number of active Pods can momentarily go up or down.

The answer can be the `Stateful` kubernetes object to have a reliable singleton service. These services are connected to message brokers, relational databases, file servers that are either on the edge or on another Pod. A regular service with `type: ClusterIP` creates a virtual IP and performs load balancing among all Pod instances that its selector matches. In the case of Singleton service since there must be one active Pod behind the service it is better to use `Headless Service` by setting both `type: ClusterIP` and `clusterIP: none` in the service definition. In which by the DNS query in the cluster the IP of the Pod(s) is returned not the services virtual IP which if we create a headless service with the name `my-singleton` in the default namespace we can query the following name and get the Pods addresses directly:
```text
my-singleton.defautl.svc.cluster.local
```

2. In-Appication Locking: This is handled through a distribution lock. Whenever a service instance or a component inside the instance is activated, it can try to acquire a lock, and if it succeeds, the service becomes active. Any subsequent service instance that fails to acquire the lock waits and continuously tries to get the lock in case currently active service releases it. A lot of services use this approach to achieve high availability such as ActiveMQ. For this the containerized application must be written with this implementation in mind. 

## Pod distribution budget
The `PodDistributionBudget` functionality of k8s that provides a complementary and somewhat opposite functionalitym limiting the number of instances that are simultaneously down for maintanence. `PodDistributionBudget` ensures a certain number or percentage of Pods will not voluntarily be evicted from a node at any one point in time. Voluntarily means an eviction that can be delayed for a particular time which is predictable for example `kubectl drain`.

`PodDisruptionBudget` is useful for quorom-based application that require a minimum number of replicas running at all times to ensure a quorum. For singleton service we need to set either of `maxUnavailable: 0` or `minAvailable: 100%`. To achieve a singleton service in Kubernetes we can combine an Stateful resource with a headless service with a PodDistributionBudget resource.

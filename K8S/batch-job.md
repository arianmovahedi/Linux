# Batch Job
Batch jobs are based on the Job object resources that run short-lived puds reliably until completion. Running bare Pods is discouraged since in an event of a fail the pod is not restarted, while ReplicaSets are for creating Pods that we expect to run continously without any sort of scaling and the lifecycle of the Pod is managed in this resource. DaemonSets are created to run a single Pod on every node and used for managing platform capabilities such as monitoring, log aggregation, storage containers and more. All these jobs are long running and their processes are not meant to stop however, in some cases thare is a need to perform a predefined finite unit of work reliabley and then shut down the container. For these sort of tasks kubernetes provides `Job` resources. We can combine it with Job and Pod directives to make use of health probes, automated placement and more.

A kubernetes Job is similar to a ReplicaSet as it create one or more Pods and ensures they run successfully, however the difference is that once the expected number of Pods terminate successfully, the Job is considered complete and no additional Pods are started. In the batch Jobs the value to the `spec.template.spec.restartPolicy` can be either `Never` or `OnFailure` while for ReplicaSets the default value is `Always`.

A Job is not ephemeral in-memory task and is a persisted one that survives cluster restarts. When a Job is done its Pods are not deleted for later inspection but we can define the `spec.ttlSecondsAfterFinished` for the cluster to garbage collect them later.

A job can be suspended by setting the field `spec.suspended` to true in this case all active Pods are deleted and restarted if a Job resumes. 

The default values of `spec.parallelism` and `spec.completions` are set to `1`. To work with a queue the container exiting clause must be that it can't find anymore item in the queue to process and we must use the `spec.completions` to 1 while the `spec.parallelism` to the amount of workers that is required as soon as the first worker Pod finds no other item to process and other processes are done it means the queue is empty and the Pod exited with a completion and the job is considered complete.

An indexed job allows the Pods to be indexed from 0 to the number of `spec.completions` -1 and achieved by setting the `spec.completionMode` to the `Indexed` value and the index is accessible to the Pod that is going to be run with the `batch.kubernetes.io/job-completion-index` annotation or directly via the environment variable `JOB_COMPLETION_INDEX` that is set to the index associated with this Pod. This allow the Pods to take a chunk of the work and do the associated work without external synchronization.
